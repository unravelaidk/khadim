# Product

## Register

product

## Platform

web

## Users

Khadim serves three connected audiences. Its primary audience is office workers and small-business operators who want to delegate repetitive computer work in plain language without learning an automation framework. Power users such as IT analysts and automation engineers need to inspect, edit, test, and schedule multi-step automations. Enterprise users such as IT leads and platform engineers need managed agents, auditability, controlled environments, and fleet-level visibility.

Users work in a desktop command center where chat, artifacts, tools, models, and execution history stay attached to a local project. The interface should make the common path approachable while keeping the underlying scripts, state, and controls available when precision matters.

## Product Purpose

Khadim is an open-source, local-first platform for creating and running agentic automations. Agents translate plain-language goals into executable scripts, observe results, adapt when an interface or edge case changes, and retry under user supervision.

Success means a user can move from intent to a dependable automation without assembling rigid RPA blocks, while retaining direct control over artifacts, credentials, runners, approvals, and generated code. Chat and Studio should feel like one continuous workspace rather than separate products.

## Positioning

Khadim makes automation resilient by letting local agents write, run, inspect, and repair the scripts that perform the work.

## Brand Personality

Calm, capable, and precise. The product should feel like a quiet command center that can remain open all day: approachable for a first automation, legible during a long run, and rigorous enough for technical inspection. Its voice is direct, practical, and proactive without sounding promotional or theatrical.

## Anti-references

Khadim should not resemble a crypto dashboard, a glowing terminal fantasy, a generic stack of glass cards, or a decorative AI playground. Avoid rigid no-code block-builder conventions that obscure the executable work, and avoid interfaces that hide essential control behind AI-only interactions. Novelty must never displace familiar desktop affordances, clear execution state, or direct editing.

## Design Principles

1. **Start with intent, reveal control.** Make plain-language delegation the easiest entry point, then progressively expose scripts, models, tools, approvals, and runtime detail as the task demands.
2. **Keep the user in command.** AI accelerates creation and repair, but direct editing, explicit approvals, understandable state, and reversible actions remain first-class.
3. **Show the work.** Runs, tool activity, artifact changes, failures, and retries should be inspectable enough to earn trust without overwhelming the primary task.
4. **Preserve project continuity.** Chat, Studio, artifacts, agents, and execution history share one project context so work can move between conversation and direct manipulation without losing state.
5. **Design for resilient operation.** Treat errors, changing interfaces, interrupted runs, and recovery as normal product states rather than exceptional afterthoughts.

## Accessibility & Inclusion

Target WCAG 2.2 AA for the renderer. Preserve complete keyboard navigation, visible focus, readable supporting text, sufficient contrast, and semantic names for compact or icon-only controls. Respect reduced-motion, reduced-transparency, and increased-contrast preferences. Dense operational views must remain legible, with a minimum persistent text size of 11px and density created through spacing rather than unreadably small type.
